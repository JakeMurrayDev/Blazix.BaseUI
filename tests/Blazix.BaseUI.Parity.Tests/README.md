# Component parity harness

Renders the same component demo twice — once from base-ui (React), once from Blazix.BaseUI (Blazor,
in both Server and WASM render modes) — and diffs the two. One C# Playwright runner drives both legs
in the same browser context, so a difference is attributable to the components rather than to the
tooling around them.

Design and rationale: [`docs/superpowers/specs/2026-07-27-component-parity-harness-design.md`](../../docs/superpowers/specs/2026-07-27-component-parity-harness-design.md).

## What is compared

Per fixture, per step: DOM structure, attributes (excluding `style` and `class`), ARIA snapshot,
allowlisted computed styles, CSS custom properties, geometry, focus position, console output,
`data-blazix-*` marker classification, animation timeline, screenshot pixels, and API surface.

Generated ids are symbolized rather than stripped, so `aria-controls` pointing at the wrong node is
still a failure. `class` is reported as `Info` only — `size-3.5` and `h-3.5 w-3.5` are class-set
different but computed-style identical, so computed style is the real assertion.

Unwaived `Error` findings fail the run. Accepted deviations live in `waivers/waivers.json` and each
requires a `reason`.

## Environment variables

| Variable | Effect |
| --- | --- |
| `PARITY_LIVE=1` | Recapture the React leg in-process instead of loading committed baselines |
| `PARITY_WRITE_BASELINES=1` | Persist the captured React leg to `baselines/` (implies `PARITY_LIVE`) |
| `PARITY_FIXTURES=<glob>` | Restrict the run to matching fixture ids, e.g. `popover/*` |
| `PARITY_REPORT_DIR=<path>` | Override the report output folder |
| `PARITY_BASE_UI_PATH=<path>` | Absolute path to the `.base-ui` checkout, when auto-detection fails |

## The stylesheet

Both sides load a single `parity.css`, generated by one Tailwind v4 build that scans **both** source
trees — the React demos under `.base-ui` and the Blazor fixtures under
`Blazix.BaseUI.Parity.Tests.Client/`. This is a correctness requirement, not a convenience: if the
two sides resolved Tailwind utilities from separate configurations, a configuration difference would
surface as a fake component discrepancy.

Both sides reach that one file over HTTP: the Blazor host links it from `wwwroot`, and
`react-fixtures/index.html` links `/parity.css` — rooted, because the bundle is mounted under
`/react/` on the same origin. The React bundle deliberately has **no Tailwind Vite plugin** and
`src/parity.css` is deliberately **not** imported from `src/main.tsx`. Either would make Vite emit a
second stylesheet, which is what the single-build guarantee exists to prevent; `src/parity.css` is
the Tailwind CLI's input only.

Tailwind v4 is CSS-first — there is no `tailwind.config.js`. Configuration lives in
`react-fixtures/src/parity.css`. Tailwind cannot read an environment variable, so
`react-fixtures/scripts/resolve-base-ui-source.mjs` writes the resolved base-ui path into a generated
`src/base-ui-source.css` (gitignored) that `parity.css` imports.

Regenerate after changing fixture classes, bumping base-ui, or bumping Tailwind:

```bash
cd tests/Blazix.BaseUI.Parity.Tests/react-fixtures
pnpm install
pnpm parity:css
```

The output, `Blazix.BaseUI.Parity.Tests/wwwroot/parity.css`, **is committed** — `dotnet test` does not
need Node.

## Refreshing baselines

The React captures in `baselines/` are committed so the suite runs without `.base-ui` present.
Rebuild the React bundle, then recapture:

```bash
cd tests/Blazix.BaseUI.Parity.Tests/react-fixtures
pnpm parity:build
cd ..
PARITY_WRITE_BASELINES=1 dotnet test
```

Each baseline records the base-ui git SHA and a content hash of the demo files it derives from. If
the built bundle's hashes do not match, the run fails with `baselines stale — run pnpm parity:baseline`
rather than diffing against stale output. The `parity:baseline` script named in that message is added
by a later task; until it exists, the two-command recipe above is its equivalent.

## When `.base-ui` is required

`.base-ui` is a gitignored checkout at the **main repository root**, so it is absent from git
worktrees; `resolve-base-ui-source.mjs` walks up to 12 levels to find it, and `PARITY_BASE_UI_PATH`
overrides the search.

It is needed only for `pnpm parity:css`, `pnpm parity:build`, and runs with `PARITY_LIVE=1` or
`PARITY_WRITE_BASELINES=1`. A plain `dotnet test` uses the committed baselines and the committed
`parity.css`, and needs neither `.base-ui` nor Node.
